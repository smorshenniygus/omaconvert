# OmaConvert: объединение веток и ограниченные workers

Статус: проект спецификации для согласования. Реализация и испытания ещё не выполнены.

## Цель и границы

Объединить защиты релиза 1.3.5 с тремя локальными улучшениями main, затем сделать единый обязательный механизм ограничения обработки медиа. Злонамеренный или повреждённый файл должен завершать своё задание контролируемой ошибкой, не создавать неограниченное потребление памяти в Python или оболочке и не оставлять работающие инструменты.

Сохранить интерфейс, клавиатуру, CLI, медиа-семантику, качество, ограничение итогового размера, неизменность исходников и публикацию без перезаписи существующих файлов. Новые ограничения могут отклонять слишком ресурсоёмкие задания с понятным объяснением. Тихое ухудшение качества не допускается.

Это защита от исчерпания ресурсов, а не полная песочница против выполнения произвольного кода после эксплуатации декодера. Изоляция файловой системы и сети через bubblewrap — отдельный следующий этап, не условие завершения этой итерации. Списки разрешённых форматов и протоколов сохраняются.

Без публикации релиза, сообщений в GitHub, установки плагина или перезапуска рабочего шелла на этом этапе. Проверка UI — в отдельном тестовом экземпляре.

## 2. Граница исполнения

QML запускает небольшой контроллер через существующий CLI. Контроллер не декодирует медиа и не накапливает полный вывод инструментов. Он запускает media worker, ограничивает обмен, отслеживает отмену и сообщает конечный исход.

Worker включает Python-обработку задания, FFmpeg/ffprobe/gifsicle и все их дочерние процессы в одну временную пользовательскую cgroup **до первого чтения содержимого медиа**. Внутри batch общий бюджет распространяется на все параллельные элементы. Подготовка возможностей инструментов также выполняется под ограничениями и остаётся отменяемой.

Все запущенные OmaConvert workers одного пользователя относятся к общей ограниченной группе приложения; подгруппы заданий имеют дополнительные ограничения. Общая группа не включает QML/Quickshell. Несколько CLI и одновременное превью не должны умножать общий предел памяти. Общая группа существует только во время активной обработки; постоянные unit-файлы и автозапуск не создаются.

Для этой версии поддерживаемый механизм — user systemd с действующим контроллером памяти cgroup v2. Наличие бинарника или сокета не считается доказательством. Проверять применённые лимиты и принадлежность worker группе перед разрешением обработки. Если это невозможно — контролируемый отказ без запуска декодера. Автоматический fallback к неограниченному запуску или к неэквивалентному prlimit убрать. --version, --help и диагностика зависимости должны работать без запуска медиа.

Exec-helper и supervision сохраняют отмену и завершение при смерти родителя. При выборе конкретного режима systemd не предполагать, что scope/service сохраняет PID и родительство одинаково: доказать дерево процессов тестами. При гибели контроллера должен завершиться весь worker, а не только внешний systemd-run.

## 3. Политика ресурсов

Начальная политика, подлежащая проверке на контрольном наборе:

- Общий предел приложения: 60% эффективной доступной ёмкости памяти, но с резервом не менее 1 GiB. Эффективная ёмкость — минимум физической RAM и конечных лимитов предков cgroup. Не использовать минимальный бюджет, который может превысить этот предел.
- `MemorySwapMax=0` для workers; общий бюджет включает Python и потомков.
- Автоматическое исследование/превью: не более 2 GiB на задание и никогда не больше общего бюджета. Не более одного активного автоматического медиа-задания на экземпляр UI; новый запрос отменяет устаревший. Общий предел приложения действует и между экземплярами.
- Конвертация: общий доступный бюджет делится между активными заданиями; batch из трёх картинок не получает три независимых бюджета по 60%. Сначала сохранить существующую параллельность внутри одного ограниченного batch. При недостатке бюджета новые конвертации ждут с возможностью отмены.
- Probe/preview: общий абсолютный срок 120 секунд, включая запуск worker. Конвертация сохраняет watchdog отсутствия прогресса 300 секунд и существующую настройку, но изменение watchdog не снимает лимит памяти.
- Превышение лимита одного задания останавливает всё его дерево. Задания не перезапускаются автоматически с повышенным пределом.

Временный недостаток свободной RAM может вызвать ошибку даже ниже лимита; не обещать абсолютную неуязвимость рабочего стола к общей нагрузке других программ. Параметры увеличивать только после измерений и обновления этой спецификации.

## 4. Ограниченный обмен данными

- `ffprobe` запрашивает только поля, которые реально использует MediaInfo, включая rotation, SAR, disposition и признаки изображений/анимаций.
- stdout capture: верхняя граница 1 MiB на ответ инструмента; проверять размер при чтении байтов, до декодирования/JSON. Превышение останавливает процесс и завершает операцию ошибкой. Для capability discovery проверить достаточность этого бюджета на установленном FFmpeg.
- Прогресс FFmpeg: строка не более 16 KiB; ограничение действует до выделения неограниченной строки.
- JSONL к QML: не более 64 KiB на событие. Большие коллекции передавать ограниченными порциями; существующие потребители batch должны сохранять порядок и идентичность элементов. Нельзя просто обрезать сериализованный JSON.
- stderr: хранить хвост не более 8 KiB, непрерывно вычитывать поток. Контроллер проверяет поток worker до передачи QML; диагностика не идёт напрямую в SplitParser.
- Числовые поля должны быть конечными и допустимыми. Относиться к stdout worker как к данным, а не как к готовому доверенному протоколу.
- Превью: PNG не более 320 пикселей по каждой стороне и 1 MiB на диске, без переноса исходных метаданных. Разрешать UI только результат текущего задания из его приватной рабочей папки, после проверки размера и заголовка. Не декодировать исходный файл средствами Qt.

## 5. Завершение и файлы

Различать `cancelled`, `timeout`, `memory-limit`, `output-limit`, `worker-failed`, `protection-unavailable`. Внешние имена событий CLI сохраняются, причины добавляются совместимо.

`SIGKILL` сам по себе не доказывает OOM. Для memory-limit нужны сведения systemd/cgroup, снятые до удаления группы; при отсутствии доказательства сообщать нейтральную ошибку завершения worker. На один запрос — один конечный исход.

Рабочие каталоги приватные с момента создания. Публикация следует только после полной проверки результата; лимит, отмена или crash не публикуют текущий частичный результат. Уже успешно опубликованные элементы batch сохраняются. Уборка после смерти worker выполняется контроллером; после смерти контроллера следующая сессия убирает только распознанные собственные остатки, не чужие файлы и не каталоги активных заданий.

## 6. PNG-бомба и регрессии

В репозитории хранится генератор тестового PNG, а не готовый опасный файл. Он создаёт корректное маленькое изображение с множеством zTXt-чанков с разными ключами. Число чанков и суммарный заявленный распакованный объём ограничены параметрами генератора; сам генератор использует небольшой повторяемый блок и не выделяет весь распакованный объём.

Два уровня:

1. Обычный набор: небольшая фикстура для проверки структуры, CRC, параметров генератора и обычного чтения. Без гигабайтного распаковывания.
2. Явный security integration test: PNG с суммарным потенциальным объёмом метаданных 1 GiB, worker с тестовым пределом 256 MiB, внешний hard timeout 30 секунд. Файл создаётся в приватном временном каталоге вне папок, индексируемых/просматриваемых UI, и не открывается внешним просмотрщиком.

До второго уровня отдельный синтетический allocator доказывает фактическое принудительное ограничение тестовой cgroup. Если проверка недоступна или провалилась, бомба не запускается; это не успешная проверка защиты. На CI такой пропуск отмечается явно, а для релизной приёмки требуется реальный успешный прогон.

Проверить реальные пути `--probe`, preview и выбора файла в изолированном QML harness. Если установленный FFmpeg отвергает или безопасно пропускает метаданные, это допустимый исход; доказательством самого лимита остаётся allocator. Не требовать искусственно OOM от исправленного декодера.

Снимать peak памяти cgroup (включая Python), сведения OOM, длительность, код/причину завершения, состояние дерева процессов и остатки файлов. Учитывать документированные краткие превышения memory.max: фиксировать измеренное значение и не объявлять точность до байта. После завершения не должно оставаться процессов задания и опубликованного частичного результата.

Дополнительные обязательные сценарии: stdout без конца и без перевода строки; слишком большой JSON; конкурентный batch и второй CLI; отмена в очереди/при запуске/при кодировании; смерть контроллера; недоступный systemd или memory controller; внешний SIGKILL без OOM; повторное открытие после ошибки; старое превью после смены входа.

## 7. Приёмка

1. Объединённая база проходит `PYTHONDONTWRITEBYTECODE=1 bash scripts/check.sh` до нового рефакторинга.
2. Тесты новых контрактов сначала демонстрируют отсутствующую защиту на безопасных ограниченных сценариях, затем проходят с реализацией.
3. Security integration tests действительно работают под cgroup, а не только проверяют список аргументов или mocks.
4. Обычные изображения, прозрачность, поворот, HDR/SDR, GIF, MP4/WebM, 4K и batch сохраняют корректный результат. До/после сравниваются время, peak RAM, размеры, декодируемость и действующие тесты качества; алгоритмы кодирования не менять ради прохождения ограничения.
5. Повторный общий check.sh; отдельный визуальный и клавиатурный прогон UI, без установки в рабочий шелл.
6. Итоговый отчёт разделяет автоматическую, реальную cgroup и UI-проверку, указывает ограничения и оставшийся этап файловой/сетевой песочницы. Одобрение маркетплейса не обещается.
